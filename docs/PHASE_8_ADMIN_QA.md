# Phase 8 — Audit Log & Administrative Settings QA

## Scope

Phase 8 completes the remaining Super Admin administration surfaces without
creating a second settings model. The implementation binds directly to the
existing operational schema used by Attendance, Presence, Scrum and Requests.

Completed areas:

- immutable, searchable Audit Log
- company-wide EMS settings
- work-schedule administration
- holiday administration
- leave-type administration
- environment isolation for audit history
- automatic audit evidence for all Phase 8 configuration mutations
- responsive and accessible Super Admin UI

## Audit Log

The Audit Log reads the existing `audit_logs` table. Phase 8 adds an
`is_test_account` environment marker and scopes Super Admin reads/inserts to
the current EMS environment.

The page supports:

- free-text search
- exact action filtering
- exact entity filtering
- actor filtering
- from/to dates in the current profile timezone
- 25-row pagination
- actor name and employee code
- local timestamps
- readable before/after field changes
- expandable raw recorded data when a field diff is not applicable

Audit rows remain immutable. Authenticated UPDATE and DELETE privileges are
removed and the existing immutable trigger remains enabled.

## Company settings

The settings form controls the canonical singleton `company_settings` row:

- company name and timezone
- default schedule
- default daily target
- grace period
- heartbeat interval
- idle threshold
- away threshold
- heartbeat stale threshold
- automatic sign-off threshold
- Scrum requirement at sign-in
- Scrum requirement at sign-off
- final request approval requirement

The database rejects invalid threshold ordering. Heartbeat staleness must exceed
the heartbeat interval, Away must exceed Idle, and automatic sign-off must
exceed Away.

## Work schedules

Super Admin can create/edit/activate/deactivate normal schedules.

Supported models:

- fixed
- flexible
- flexible with core hours

Validation covers target minutes, grace, IANA timezone and required clock fields.
Irrelevant clock fields are normalized to NULL.

Schedules generated by approved Phase 6 requests remain read-only workflow
history. A schedule selected as the company default cannot be deactivated until
another default is chosen. Deactivation preserves existing assignments and
historical workdays.

The Phase 8 UI mirrors the database guard by identifying the current default
schedule and suppressing its deactivation control until another default is
selected. This avoids presenting an action that is known to be rejected by the
canonical workflow.

## Holidays

Super Admin can create and edit company-wide or department holidays. New
holidays cannot be created in the past. Historical holiday date/scope cannot be
rewritten, and past holidays cannot be deleted.

The canonical `holidays` table continues to feed attendance calculation and
leave working-day calculation.

The UI uses the configured company timezone to prevent new past-dated holidays
at the form boundary. Existing past holidays remain editable only through the
server-side historical rules, and the destructive delete control is not shown
for already historical dates.

## Leave types

Super Admin can create/edit/activate/deactivate leave types, including:

- code and name
- paid/unpaid
- reason requirement
- default annual entitlement

Existing attachment flags are preserved if historical data contains them; Phase
8 does not invent an attachment-storage workflow.

Leave types are deactivated instead of deleted. Existing requests and leave
ledger rows keep their foreign-key history. The final active leave type cannot
be deactivated. The UI mirrors that invariant and does not offer a deactivation
action when only one active leave type remains.

## Audit capture

Database triggers automatically create immutable audit evidence for:

- company settings changes
- work schedule creation/update/status changes
- holiday creation/update/deletion
- leave type creation/update/status changes

Server workflows propagate an optional human audit note through
`app.phase8_reason`, and reset that transaction-local value after successful
or failed operations.
